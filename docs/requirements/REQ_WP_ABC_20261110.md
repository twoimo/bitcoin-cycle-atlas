## 0. 이 문서를 쓰는 방법

1. Pro 스레드에 **이 문서 1개 + §5의 첨부 파일**을 올린다. 첨부는 §5의 "최소 세트"부터.
2. Pro에게는 §6의 복붙용 프롬프트를 함께 보낸다.
3. 세 작업은 **브랜치·커밋·PR을 절대 섞지 않는다.**
   - **WP-B(요구사항 문서)** 를 먼저 끝낸다. 짧고, 다른 작업의 기준 문서가 된다.
   - **WP-A(컨퍼런스 복습 페이지)** 는 자산 파이프라인부터 길다. WP-B 완료 후 착수한다.
   - **WP-C(compare 레거시 진입의 표준 셸 통합, §2A)** 는 셸 라우팅을 건드리므로 WP-A와 파일이 겹친다. **WP-A 커밋이 끝난 뒤** 별도 브랜치로 착수한다.
4. 각 WP는 "산출물 + 검증 증거 + 브랜치/커밋 해시"로 끝난다. 말로 된 완료 보고는 인정하지 않는다.

## 2. WP-A — 컨퍼런스 복습 페이지 (2열: 장표 + 자막 동기화)

### A-1. 목표

배포 사이트의 **우측 패널(우측 내비게이션)** 에 항목 하나를 추가한다.

- 좌측 열: 플스포 투자 컨퍼런스 **장표(PDF)가 반응형으로** 표시된다.
- 우측 열: **Plaud 녹음 자막이 여러 행으로** 표시되고, 장표 화면과 **시간 동기화**된다.
- 재생 버튼 등 컨트롤로 **시간 순서대로 장표가 넘어가면서 녹음 전체가 재생**된다.
- 목적은 **컨퍼런스 복습**이다. 발표를 다시 보며 장표와 발화를 동시에 따라갈 수 있어야 한다.
- **290쪽 최종본**과 **R17 편집형 재구성(257쪽)** 두 덱을 각각 구성하고, 화면에서 전환할 수 있어야 한다.
- 녹음과 싱크를 맞출 장표가 없는 구간은 **보조 장표를 새로 만들어 넣어도 된다**(원본 덱은 수정하지 않는다. A-6 참조).

### A-2. 현재 사이트 구조 (근거)

| 요소 | 현재 상태 | 근거 파일 |

| 우측 내비게이션 | `주요 페이지` 6개: 가격 차트·시장 분석·리서치·자산 비교·공모주·릴레이 콘텐츠 (내비에 노출되는 항목만). 전체 페이지 레지스트리는 12개(시장 하위 탭 포함) | `dist/atlas-navigation.js`의 `atlasPages` / `atlasNavigationPages` |

- 페이지 본문은 셸을 유지한 채 메인 영역에서 렌더한다(`?page=conference`). 별도 전체화면 앱으로 분리하지 않는다(모바일 예외는 A-5 레이아웃 표).

### A-4. 데이터 계약 — `timeline.json`

페이지가 읽는 단일 진실은 `timeline.json` 하나다. UI는 이 파일 없이 동작하지 않는다.

```json
{
  "schemaVersion": 1,
  "event": {
    "id": "plspo-2026-10-31",
    "title": "플스포 투자 컨퍼런스 2026",
    "date": "2026-10-31",
    "timezone": "Asia/Seoul",
    "clockStart": "12:33:00",
    "clockEnd": "18:13:00"
  },
  "audio": [
    { "id": "plaud-1", "file": "audio/plaud-1.m4a", "clockStart": "12:33:00", "durationSec": 18000 },
    { "id": "plaud-2", "file": "audio/plaud-2.m4a", "clockStart": "17:33:00", "durationSec": 2400 }
  ],
  "decks": [
    { "id": "final-290", "label": "최종본 290쪽", "pages": 290, "dir": "pages/final" },
    { "id": "r17-257", "label": "R17 편집형 257쪽", "pages": 257, "dir": "pages/r17" }
  ],
  "talks": [
    {
      "id": "01",
      "title": "규동산 — 아파트 매매 거래량으로 보는 매수 타이밍",
      "t0": 0, "t1": 2220,
      "pageRange": { "final-290": [12, 26], "r17-257": [11, 24] }
    }
  ],
  "segments": [
    {
      "t0": 484.8, "t1": 704.3,
      "text": "다시 한번 안내 말씀드리겠습니다. …",
      "source": "plaud1#1",
      "talk": "01",
      "page": { "final-290": 12, "r17-257": 11 }
    }
  ]
}
```

**규칙**

1. `t0`/`t1`은 이벤트 시작(12:33:00) 기준 초. 파일별 SRT 오프셋을 이미 반영한 값이다.
2. `segments`는 **자막 원문을 자르거나 합치지 않는다.** SRT 세그먼트 1개 = 행 1개를 기본으로 한다. 너무 긴 세그먼트(예: 3분짜리 안내 방송)는 화면 표시용으로만 문장 단위 분할을 허용하되, 원본 세그먼트 id를 `source`에 남긴다.
3. `page`가 `null`이면 "이 구간에 맞는 장표 없음"이다. 직전 장표를 유지하고 UI에 표시한다.
4. 덱별 페이지 번호는 1-based. 290쪽 덱과 257쪽 덱은 같은 발표라도 페이지 번호가 다르므로 반드시 덱별로 매핑한다.
5. 자막 100%가 타임라인에 존재해야 한다(누락 0). 검증 스크립트로 강제한다.
6. 오디오 길이와 `t1` 합이 맞아야 한다(마지막 세그먼트 t1 ≤ 오디오 총 길이).

### A-5. 화면 계약

#### 레이아웃

| 뷰포트 | 레이아웃 |
|---|---|
| ≥1280 | 2열: 장표 56% / 자막 44%, 각 열 독립 스크롤, 상단 고정 컨트롤 바 |
| 1024–1279 | 2열 유지, 장표 52% / 자막 48% |
| 768–1023 | 2열 축소 또는 상하 분할(장표 위·자막 아래), 오디오 바 고정 |
| ≤767 | 1열 + `장표 / 자막` 탭 전환, 오디오 바는 하단 고정 |
| 390·320 | 1열 탭, 컨트롤은 44px 이상, 가로 오버플로 0 |

#### 컨트롤 (최소)

- 재생/일시정지, −10초/+10초, 진행 바(전체 이벤트 기준, 세션 경계 표시), 현재 시각/총 길이.
- 재생 속도 0.75× / 1× / 1.25× / 1.5× / 2×.
- 이전/다음 **세션**, 이전/다음 **장표**.
- `자막 따라가기` 토글(자동 스크롤), `장표 자동 넘김` 토글.
- 덱 선택(최종본 290 / R17 257).
- 자막 검색(현재 발화로 점프), 발표 목록 드롭다운.

#### 동작

- 자막 행 클릭 → 해당 시각으로 seek + 해당 장표로 이동.
- 장표 클릭(또는 페이지 번호 입력) → 그 장표가 처음 나오는 세그먼트로 seek.
- 재생 중에는 `현재 시각 이하의 마지막 세그먼트`의 page로 장표를 갱신한다. 페이지가 바뀔 때 깜빡임/이중 렌더가 없어야 한다.
- 덱을 바꿔도 **현재 재생 시각은 유지**되고, 해당 덱의 매핑 페이지로 이동한다. 매핑이 없으면 "이 덱에 해당 장표 없음" 배지를 띄운다.
- 딥링크: `?page=conference&t=3725&deck=r17-257`로 진입하면 그 시각·덱·장표로 복원한다.
- 새로고침·뒤로가기에서 재생 상태가 깨지지 않는다(자동재생은 하지 않는다).

#### 접근성

- 모든 컨트롤 키보드 도달 가능, 포커스 링 유지.
- Space 재생/정지, ←/→ 5초, Shift+←/→ 30초, `[`/`]` 장표 이동, `F` 따라가기, `D` 덱 전환.
- 현재 자막은 `aria-live="polite"`로 1회만 읽힌다(중복 낭독 금지).
- 자막 텍스트는 선택·복사 가능해야 한다.

### A-6. 장표가 없는 구간 처리 (보조 장표)

- 자막은 있으나 매핑 가능한 장표가 없는 구간(휴식, 진행 안내, Q&A, 잡담)이 있으면 **보조 장표를 생성해 넣어도 된다.**
- 보조 장표는 **원본 덱을 수정하지 않고** 별도 자산(`pages/generated/`)으로 만들고 `timeline.json`에서만 참조한다.
- 표지는 최소 텍스트(구간명·시각)와 사이트 다크 테마를 따르고, `generated: true`로 표시해 원본 장표와 구분한다.
- 보조 장표를 넣었다면 PR에 "생성 장표 N장, 근거 구간"표를 남긴다.

## 3. WP-B — 요구사항 문서 갱신 (릴레이 멀티 에이전트 RAG)

### B-0. 역할

너는 `twoimo/bitcoin-cycle-atlas` 저장소의 **요구사항 문서를 갱신하는 설계 담당**이다.
**문서만 수정한다. 구현 코드는 건드리지 않는다.**

### B-1. 현재 상태 (먼저 확인할 것)

- 기준 브랜치: `docs/requirements-auth-relay-rag-20261109` (팁 `e95ba91`). **`docs/requirements/*`는 main에 없다.**
- 대상: `docs/requirements/REQ_RELAY_RAG_20261109.md` (초안, 구현 전, WP9)
- 인덱스: `docs/requirements/README.md`, 기록: `docs/WORKLOG.md`
- 이 문서의 기존 확정 계약(삭제·하향 금지):
  - §2 3열 레이아웃(접이식·1024/768/390)
  - §3 8단계 단일 RAG
  - §6 임계값: Recall@10 ≥ 0.85, Faithfulness ≥ 0.90, Citation precision ≥ 0.90, p95 ≤ 6s, 첫 토큰 ≤ 1.5s
  - §9 수용 기준 1~6, §10 마일스톤 R1~R5
  - §8 보안 원칙
- 릴레이 소스 room id: `telegram`(소수의견) / `naver`(플스포 인생의 방) / `hankyung`(모바일한경)

### B-2. 이번 요청

3열 AI를 **단일 RAG에서 소스별 멀티 에이전트 + 종합 에이전트 구조로 확장**한다.

1. 사용자 질문에 여러 에이전트가 답할 수 있어야 한다. 최소 3개: 소수의견 / 플스포 인생의 방 / 한국경제.
2. 에이전트 하나만 답하면 되는 질문은 그 에이전트가 바로 답한다(종합 호출 없음, 비용 절감).
3. 여러 에이전트가 답하는 경우, 그 의견을 종합해 하나로 정리하는 별도 에이전트가 필요하다.

### B-3. 반드시 지킬 것

- 기존 §2 레이아웃 계약, §5 대화 저장 스키마, §6 임계값, §8 보안 원칙은 **삭제하거나 낮추지 않는다. 추가만 한다.**
- 기존 번호 체계를 깨지 말고 하위 절(3.1, 6.1, 7.2 …)과 이어지는 번호(9-7 이후, 10의 R2.5)로 붙인다.
- **이름 충돌 주의**: 소스 채널 이름이 `소수의견`이라 "소수의견 에이전트"가 소스 전담인지 반대 관점 전담인지 모호해진다.
  `src-minority`(소스 전담)와 `dissent`(반대 관점)를 **분리해서** 정의하고, 이번 요구는 소스 전담 3개 + 종합 1개로 해석한다.
- 인용은 기존 `[n]` + 원문 링크 형식을 유지한다.
- 에이전트가 늘어나도 기존 p95 6s·첫 토큰 1.5s를 넘기지 않을 예산 규칙을 같은 절에 적는다.

### B-4. 새로 쓸 절 (번호와 필드까지 지정)

#### §3.1 에이전트 레지스트리 (표)

컬럼: `agent_id | 표시명 | 담당 source(room id) | 역할·말투 | 검색 범위 | 금지사항`

최소 4행: `src-minority`, `src-pspo`, `src-hankyung`, `synthesizer`. 선택적으로 `dissent`.

- 각 에이전트는 **자기 소스 밖 문서를 인용하면 실패**로 정의한다.
- 말투는 소스 성격에 고정: 텔레그램=속보·구어체, 아티클=해설체, 지면=사실 위주.

#### §3.2 라우터

- 1차 규칙: 소스명·종목·기간·채널 직접 언급. 2차: LLM 분류.
- 출력 JSON: `{ agents: string[], mode: "single"|"multi", reason: string, confidence: 0..1 }`
- 판정 규칙 최소 4개: 한 소스만 언급 / 둘 이상 언급 / "비교·종합·각각" 류 표현 / 소스 무관 일반 질문.
- 폴백: `confidence < 0.6` 또는 라우터 호출 실패 시 3개 전부.
- 라우터 프롬프트에 "라우팅만 하고 답하지 말 것" 명시.

#### §3.3 소스 에이전트 계약

- 입력: 질문 + 스레드 맥락 + 자기 소스 상위 청크 6~8 + 수집 기간 메타.
- 출력: `{ answer, citations[], used_chunks[], confidence }`. 근거 없으면 `answer: null` + 사유(침묵 허용).

#### §3.4 종합 에이전트

- 입력: 각 소스 에이전트의 **구조화 출력**(원문 전체 아님).
- 출력 3블록 고정: ① 합의 ② 불일치(쟁점별 입장 대조) ③ 출처별 요약.
- 규칙: 소수 의견 삭제 금지(라벨로 표시), 근거 없는 주장은 종합에서 제외, 엇갈리면 판단 유보 + 양측 인용,
  종합은 **새 사실을 만들지 않고 재인용만** 한다. 인용은 `[소스:청크]`로 귀속 보존.

#### §3.5 실행·예산

- 소스 에이전트 병렬 호출(상한 3) + 종합 1회. 단일 판정 시 검색·생성 2콜 수준.
- 부분 실패: 실패 에이전트 제외하고 종합, 답변에 "X 소스 응답 실패" 표시. 전부 실패 시 "근거 없음".
- 스트리밍: 참여 에이전트 칩을 먼저 보여주고 종합 본문을 스트리밍.
- 질문당 토큰 상한, 초과 시 종합을 축약 모드로. 동일 질문 + 동일 스냅샷 해시면 캐시 재사용.

#### §3.6 UI 표현

- 답변 상단에 참여 에이전트 칩과 단일/다중 표시, 접이식 "근거 보기"(소스별 청크), 종합 블록별 접기.

#### §6.1 평가 확장 (기존 메트릭 유지 + 추가)

- `라우팅 정확도` ≥ 0.90, `소스 귀속 정확도` ≥ 0.90(인용 청크가 실제 그 소스 것인가),
- `종합 일관성`(소스 에이전트 주장과 종합문 사이 모순 0건), `단일 응답 회귀 없음`(기존 단일 RAG 대비 품질 하락 없음),
- `다중 질문 p95 ≤ 8s`는 **별도 행**으로 두고 단일 기준(6s)은 그대로 유지.
- 골든셋 층화: 단일 40 / 다중 40 / 답 없음 20.

#### §7.2 QA 케이스 (최소 8행 표: `시나리오 | 기대 | 실패 시 증상`)

단일 소스 질문 / 2소스 비교 / 3소스 종합 / 소스끼리 상충 / 한 소스에만 근거 없음 /
라우터 오분류 유도 / 에이전트 1개 실패 / 토큰 예산 초과 / 같은 질문 반복(캐시)

#### §9 수용 기준 추가 (9-7 이후로 이어서)

- 다중 판정 질문에서 2개 이상 에이전트 응답이 실제로 표시된다.
- 단일 판정 질문에서 종합 에이전트가 호출되지 않는다(로그로 확인).
- 인용 칩이 담당 소스 원문으로 연결되고 다른 소스 인용이 섞이지 않는다.
- 에이전트 실패 시 부분 결과 + 실패 표시가 나온다.
- 라우팅 정확도·소스 귀속 정확도가 골든셋에서 임계값을 넘는다.

#### §10 마일스톤

`R2.5 멀티 에이전트 + 종합`을 R2와 R3 사이에 추가하고 완료 기준을 위 수용 기준으로 연결.

#### §11 미결정 사항 추가
