## Reason and preserved boundaries

The Release workflow runs when `package.json` changes on main. Version `v1.31.2` already names commit `94a1b1dda9eb359de70747043808340da369d087` and a published release with 13 assets. Its immutable tag, saved publication manifest and asset bytes cannot identify a different source. The package and both root lockfile version fields therefore advance to `1.31.3`; both the remote tag and release endpoints for that new version returned 404 during preflight.

The first metadata-only follow-up, remote `ada2f3c645b3023f93b0f0799daf9b57481b57cc` / local `c3ce8a574daa419c85a25af392423ecc7270acc3`, exposed a second required part of the existing release convention. The replay VM fixtures resolve versioned imports using `package.json`, while active runtime imports still named `1.31.2`. [The failed ETH run](https://github.com/twoimo/bitcoin-cycle-atlas/actions/runs/42202007133) stopped in its replay tests before native acceptance. Its original log and counts are preserved in [the failure evidence directory](release-version-followup/README.md). The earlier v1.31.0 release recorded the same coupling in [the architecture worklog](../architecture-migration/WORKLOG.md).

The correction keeps the strict fixture contract and updates the current runtime query keys. It does not change a replay assertion, model rule, data value, source clock, stored forecast, release guard or dependency resolution. No tag or release asset is overwritten. The final committed head still requires the normal complete remote CI and native-browser gates before deployment and release.
