# Verify replay lifecycle and start confirmation

Preserve this promise: **settings cannot choose an unconfirmed replay start, and obsolete loads or callbacks cannot change the current fixed replay.** Also release replay ownership synchronously on terminal destroy, even during an explicit save. A pointer press confirms a bar only as an unmoved click inside the plot, every blocked control gets its prior `inert` value back, and a forecast gate that refuses or has not answered cannot enter, open or start replay. A breach can silently choose a cutoff, reveal bars from a different session or leave live controls inert after teardown.

## Run the verification

Use Node 24 or newer; the latest bounded receipt ran on Node v26.13.0. Historical pinned runtime receipts remain separate. Run from the repository root:

```sh
node verification/replay-state/verify.mjs docs/replay-state/verification.json
```

`npm run verify:chart-replay-state` and `npm run verify:formal` run the same runner but write an untracked copy to `build/replay-state.json`. They do not refresh the committed receipt.

Require all 16 controller tests to execute without skipped, canceled or todo cases. Require all 10,000 length-four playback traces (40,000 transitions, three bars) and all 259 length-zero-through-three coordinator traces (726 transitions, six actions) to pass. The reviewed observable counts are 52 controller states / 380 edges and 24 coordinator states / 78 edges. These are projections; do not call them the full private state space. Every trace runs a fresh real instance without state merging.

Require the focused destruction case to execute both completion schedules for one pending explicit save: deferred callback resumption and rejection, with two destroy calls per schedule. Require markers and prior inert state to be restored once, saved bytes to stay unchanged and late completions to leave detached controls unchanged. These schedules do not increase the exhaustive selection alphabet or establish arbitrary persistence ordering.

Require the focused manual-date cases to check both button and Enter from a resumed capture and an unconfirmed selection. Reject empty, malformed, impossible and out-of-range dates; exercise native invalidity separately. Keep the current cursor, origin, frozen forecast, snapshot digest and durable saved bytes unchanged. Check valid min/max, error recovery on input/cancel, and the existing pointer/Random/First behavior. The fixture does not prove native validity UI; require the actual keyboard browser cases separately. These cases do not extend the six-action selection alphabet.

Require the five focused guard cases. An unconfirmed selection must stay unconfirmed, with no session built, after one click on the price axis and one on the time axis. With the period footer in the phone information sheet and in the desktop layout, the sheet opener, its close action and the original period controls must stay reachable, unrelated navigation must stay blocked, and destroy must restore every prior `inert` value, including one that was already inert. A refused forecast must leave replay inactive from the toolbar entry and from exported `open` with a saved record, load no archive, build no session and keep the saved bytes. A gate that has not answered (`null`) must leave replay inactive from the toolbar entry, show the notice to press replay again once the chart is ready and load no archive. A later T3 answer must refuse as before. A gate that allows entry and then refuses before confirmation must make `start` exit replay with the refusal notice, build no session and write nothing. These cases do not extend the six-action selection alphabet. They cover a refusal known before entry and a refusal that arrives between entry and confirmation.

Require **seventeen detected real-source negative controls**: session owner, timer owner, recursive freeze, archive-end rewind, mode/model confirmation, horizon confirmation, selected-mode reentry, storage-slot/mode isolation, destruction routed through the interactive save guard, a revoked exit completion updating detached controls, manual date handlers bypassing validation, an axis click confirming a start, duplicate owner discovery overwriting a prior `inert` value, a refused forecast entering replay, a refused forecast opening replay, an unanswered gate treated as allowed, and `start` fixing a forecast without rereading the gate. Require the intended assertion, not merely a nonzero process exit. The two settings controls must report the shortest bounded counterexample: open selection, then one mode or horizon change. The destruction and manual-date cases are targeted actual-source traces, not shortest-path claims. Require the restored original controller and coordinator to pass again.

The runner creates isolated temporary copies; never edit production files to run a negative control. A selector mismatch, process error, missing import, timeout, missing enumeration or wrong failed invariant means BLOCKED. Fix the verifier's correspondence before accepting a changed guard; do not weaken the invariant.

2. Keep an unconfirmed picker distinct from a committed paused session. Preserve the settings guard when either `picking` is true or no session exists. Treat a saved-record Continue or a valid explicit date/bar choice as a separate confirmation path. Fresh entry prefers cutoff and falls back to generic history only when its cutoff slot is absent; later entry retains the selected mode. Preserve malformed or stale bytes and reject records from the other storage family instead of borrowing another slot’s hash. Require both focused saved-entry cases and their two negative controls to pass.

Mark destroy terminal before `finishExit`, revoke save ownership, restore markers/inert controls once and ignore both success and failure continuations after revocation. ## Report honestly

Report PASS, ISSUES or BLOCKED; exact command/runtime/source identities; finite trace and observable state/edge counts; detected/expected controls; shortest counterexample where actually enumerated; and any gaps. No current production caller of the returned coordinator destructor was found at the follow-up baseline; describe its repair as an exported lifecycle API case, not a demonstrated native user-flow failure.
